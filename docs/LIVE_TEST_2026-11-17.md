# Live testnet verification — 2026-11-17

Browser and hosted core flows were verified against live testnet services: funding, READY, payments before and after handoff, on-chain sends, and cooperative closure. Actual browser candidate demo screens and the deployed hosted demo both passed login, explicit node start, sending, verified message signing, and logout.

Four disposable mail.tm accounts used real email dialogs, faucet CKB, the production KeyWay API, public Fiber peers, and CKB RPC confirmation. Credentials and persistent profiles remain private, outside the repository. No existing wallet or channel database was deleted or overwritten.

## Failures found and fixed

- Returning browser devices could not restore backups over existing local databases. Restores now import into a fresh namespace and persist an active pointer before server confirmation; old databases remain intact. Canonical backup names are independent of local storage names.
- Official peers required Channel V2, rejecting native Fiber 0.9.1. Native and candidate browser runtimes now pin Fiber 0.10.1 ([release source](https://github.com/nervosnetwork/fiber/releases/tag/v0.10.1), commit d9b6bbd). The browser watchtower supports V2's 32-byte payment hashes and feature flag, with legacy fixtures retained.
- Native startup waited for an interactive migration prompt. The host snapshots stopped stores, then approves only the known non-breaking 20260618120000 → 20260925120000 update. All 29 preexisting node directories were separately snapshotted before deployment; all nine previously running nodes subsequently reported 0.10.1, with zero offline nodes.
- Incorrect confirmation codes were masked as provider outages. The API now returns only allowlisted, retryable code errors. A live incorrect-code → correct-code retry passed.
- Declined or failed signing left unsigned channel openings behind. The SDK now cancels only before submission begins. The managed API checks the caller's opening, and the managed host refuses to abandon an opening whose signed funding it has recorded, since Fiber keeps its own marker for that only while the node runs. Live cancellation passed; the host's refusal was added after the live run and is covered by a regression test, not by a live check. Once submission begins, the SDK leaves the channel intact because a lost response can conceal successful funding.
- The managed host still expected Fiber 0.9's submission state. V2 exchanges both commitments before returning the unsigned transaction. The host now accepts that state, records funding before forwarding it, and preserves the existing protections for uncertain submission outcomes.

The runner itself also needed corrections: code extraction must match the email's label rather than decimal digits in a CKB amount, and local demo builds need the registered public app ID. These were verification setup failures, not product defects.

## Not covered by this run

- A force close on a Channel V2 channel, the in-page claim of the user's share from it, and the watchtower's penalty for a revoked state. These are covered by unit tests against Fiber 0.10.1's formats only.
- A browser node database created on Fiber 0.9.1 being opened by 0.10.1.
- Opening a channel from the deployed website while it still used SDK 0.2.13.

`scripts/verify-live-wallet.mjs` runs the candidate SDK against live services; `scripts/verify-live-demo.mjs` drives actual demo screens. The candidate demo uses a local production build at the canonical origin via Playwright routing; API traffic still goes to production. At the time of the run the SDK changes were unpublished and the deployed website used SDK 0.2.13.

Temporary local API, Next and PostgreSQL servers were stopped after testing. Temporary copies of service credentials were removed; private disposable account records and browser databases were retained for recovery and future verification.
