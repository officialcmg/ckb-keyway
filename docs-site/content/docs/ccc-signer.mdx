`useCkbWallet().signer` is a [CCC](https://github.com/ckb-devrel/ccc) signer for the signed-in account. Write the CCC code you already know. KeyWay shows the user what each transaction does and signs only after they approve.

```tsx
import { ccc } from "@ckb-ccc/core";
import { useCkbWallet } from "@ckb-keyway/react";

function SendButton({ to }: { to: string }) {
  const { signer } = useCkbWallet();

  async function send() {
    if (!signer) return;
    const { script } = await ccc.Address.fromString(to, signer.client);
    const tx = ccc.Transaction.from({ outputs: [{ lock: script, capacity: ccc.fixedPointFrom(100) }] });
    await tx.completeInputsByCapacity(signer);
    await tx.completeFeeBy(signer);
    const hash = await signer.sendTransaction(tx); // approval dialog, then broadcast
  }

  return <button onClick={send} disabled={!signer}>Send 100 CKB</button>;
}
```

`signer` is undefined until the account is ready. It doesn't need Fiber. `getAddresses`, `getBalance`, `findCells`, `signMessage` and `verifyMessage` work as they do with any CCC signer. Tokens (xUDT, sUDT, including RUSD on testnet), Spore NFTs and Nervos DAO transactions work too: CCC builds them, and KeyWay signs the user's part.

## What the user approves

KeyWay's backend reads every input from the chain and decodes what the transaction does to the user's account. The approval dialog shows:

- the CKB they send or receive, and the network fee;
- token amounts by token, and NFTs sent, received, minted or burned;
- Nervos DAO deposits and withdrawals;
- each recipient, labelled as a wallet, a contract or a Fiber channel;
- any script KeyWay doesn't recognize, as a warning;
- inputs that other people must sign.

Token amounts are shown with the token's name and decimals when KeyWay knows the token (for example, "Send 25 RUSD?"), and as a short token ID with the raw amount otherwise.

The backend signs only the exact transaction it previewed, and only the user's own account. A changed transaction is refused. To use your own approval UI, pass `approveCkbTransaction` to `KeyWayProvider`. It receives the same preview (`TransactionPreview`) and returns `true` to approve.

## Signing messages

```ts
const signature = await signer.signMessage("Log in to Acme Pay");
const valid = await signer.verifyMessage("Log in to Acme Pay", signature);
```

Messages use CKB's standard `Nervos Message:` format and are shown to the user word for word. Pass `approveCkbMessage` to replace the dialog.

## Email confirmation

Users can require a code from their inbox once what leaves their account within 24 hours reaches a daily amount they choose. Each asset has its own amount: one for CKB, and one for each token. Everything signed in the last 24 hours counts toward it, so splitting a transfer into smaller ones doesn't avoid the code. With a hosted Fiber node, Fiber payments count toward the same totals. Channel funding doesn't count, because a channel can only close back to the user's own account.

It's off until the user (or your app) sets an amount. Once any amount is set, a token with no amount of its own always needs the code, and so does any cell KeyWay can't read that leaves the account.

```ts
import { ccc } from "@ckb-ccc/core";

// 500 CKB a day, in shannons.
await signer.setDailyConfirmationAmount("ckb", ccc.fixedPointFrom(500));

// 100 RUSD a day, in the token's smallest unit (RUSD has 8 decimals).
// A token is identified by its type script hash: ccc.Script.from(typeScript).hash().
const RUSD = "0x45b32a2bc4285d0a09678eb11960ddc8707bc2779887a09d482e9bfe9a2cdf52";
await signer.setDailyConfirmationAmount(RUSD, 100n * 100_000_000n);

await signer.getDailyConfirmationAmounts(); // { ckb: 50000000000n, "0x45b3…df52": 10000000000n }
await signer.setDailyConfirmationAmount("ckb", null); // remove the CKB amount
```

Changes that make confirmation stricter, such as turning it on or lowering an amount, apply at once. Changes that loosen it email the user a code first: raising or removing an amount, or giving a token its own amount while it still needs the code for every transfer. The code prompt is always the SDK's own, even when you replace the approval dialogs. `TransactionPreview.requiresEmailCode` tells your own dialog whether a code will follow.

## Silent signing

Each approval prop replaces KeyWay's dialog with your app's answer. An app that returns `true` without asking signs silently:

```tsx
<KeyWayProvider
  appId="keyway_..."
  approveCkbTransaction={() => true}
  approveCkbMessage={() => true}
>
  <App />
</KeyWayProvider>
```

The same works for the Fiber approvals (`approveFiberChannelOpen`, `approveFiberChannelClose`, `approveFiberPeerConnect`, `approveFiberChannelSettings`). Fiber payments have no dialog by default; see [Fiber node](/fiber-node#approvals).

This removes the user's confirmation of each action, so your app signs for them. Only do it for flows the user has already agreed to, such as a purchase they just confirmed in your own interface, and prefer checking the preview over returning `true` unconditionally. Sign-in and the emailed code still always appear: once the user's daily amount is reached, KeyWay asks for the code whatever your app returns.

## Limits

- Testnet only.
- The network fee may be at most 100 shannons per byte of the transaction (about 100 times the normal rate), and never less than 0.01 CKB. Normal transactions pay far less.
- Each user can start up to 10 signing requests a minute (transactions and messages together).
- Email confirmation codes: up to 5 every 10 minutes per user. Each code lasts 10 minutes and allows 5 wrong attempts.

<Callout type="warn">
The approval dialog runs inside your app's page. If your app has an XSS bug, or a user's session token leaks, an attacker could request and approve transactions until the user's 24-hour email-confirmation amount is reached. Protect your app with a strict Content Security Policy, and encourage users to set a confirmation amount.
</Callout>
